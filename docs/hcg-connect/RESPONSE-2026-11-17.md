# HCG Executable Maker: answer to the main site's 16 Nov 2026 handoff

This answers the main site's `docs/hcg-store/maker-store-integration-handoff.md` (commit `2e0cb9e`, 16 Nov 2026), §6
"Open items". It also lists what HCG Store's open PR #14 needs before Executable Maker can publish through it. These are
proposals for founder review. Executable Maker does not change central HCG policy, register clients or grant anything.
No secrets appear here.

## 2. Feature catalogue: which keys Executable Maker implements

HCG asked Executable Maker to confirm which keys it implements, and noted that the list was "proposed from the brief,
not from Maker source code".

| Central key (`hcg.executable.maker`) | Implemented? | How Executable Maker uses it |
|---|---|---|
| `support.submit` | **Yes** | Fresh `/check` before a support request is sent, in the UI and on the command line. |
| `support.attach` | **Yes** | Fresh `/check` before project files are attached. |
| `ai.use` | **Yes** | Fresh `/check` before every HCG AI request. |
| `ai.build_diagnostics` | No | Not used. |
| `build.desktop`, `package.installer`, `build.mobile` | **Not adopted (founder decision needed)** | Executable Maker's documented promise is that local builds and packaging are **free, offline and need no account**. Gating them behind a licence would break offline use and change the product's terms, so Executable Maker does not consult these keys. If the founder decides builds should be licensed, that is a separate product change with its own offline policy. Until then, please leave them `planned`/disabled, or remove them. |
| `store.upload` (class `customer`) | **Conflict, see §4** | Executable Maker implements "submit a build to HCG Store for review" (Ship to Store). That is gated today by HCG Store's **staff** publishing permission, not by a customer licence. |

The `/check` reasons `expired` (offers renewal through the HCG Store product page) and `revoked` (no purchase offer;
asks the administrator) are handled from this change on. 503 `service_unavailable` already counts as "HCG unavailable,
deny and retry". An allowed answer's `layer: null` is accepted.

## 3. Store purchase grants (`/store/grants`)

These are not used by Executable Maker; they run between HCG Store's server and HCG. The shared secret stays out of
band. Executable Maker never sees it.

## 4. Ship to Store permissions: three definitions that do not match yet (founder decision)

| Source | "May upload a build as a private draft" | "May approve a release for public" |
|---|---|---|
| HCG Store `main` (merged) | `HCG_STORE_PUBLISHER_CENTRAL_ID` (staff permission; unset) | `HCG_STORE_RELEASE_APPROVER_CENTRAL_ID` (unset) |
| HCG Store PR #14 (open, not merged) | `store.publish`, asked as `/check {product_id: <the product's central ID>, feature_key: "store.publish"}` | `store.release.approve`, same pattern |
| Main site catalogue (16 Nov) | `hcg.executable.maker` / `store.upload`, class **customer** (licence; purchasable); `hcg.store` / `store.publish` = "publish approved releases" (operational) | `hcg.store` / `store.release.approve` (operational) |

Problems:

1. **Product mismatch (blocks publishing).** HCG registered `store.publish` and `store.release.approve` only under
   product **`hcg.store`**. PR #14 asks about them under the *published* product's central ID (for example
   `hcg.executable.maker`), where they do not exist. HCG then answers `feature_unavailable`, so nobody could ever
   publish or approve a catalogue product. The fix belongs to either side: HCG Store asks with `product_id: "hcg.store"`,
   or HCG registers the operational keys per product.
2. **Meaning mismatch.** HCG Store's "publisher" permission means "may create drafts and upload". HCG's `store.publish`
   means "publish approved releases", and HCG's `store.upload` means "submit build for review". The founder should
   choose one key for uploading drafts.
3. **Class mismatch (policy).** HCG classes `store.upload` as **customer**, so it would come with a purchased licence.
   Executable Maker and HCG Store treat uploading to the Store as a **staff** permission: Executable Maker tells a
   refused person to ask their administrator and never shows a purchase option. HCG's own rule says operational
   features can never be bought. Proposal: the upload permission is an **operational** key, for example under
   `hcg.store`. If the founder instead wants customers to buy upload rights, HCG Store must check the customer licence,
   and Executable Maker would show the HCG Store link for `not_licensed`.

Executable Maker consumes only HCG Store's answer (`GET /api/v1/publishing/products` and 403 `not_publisher`). It needs
no change for any of these choices.

   licence.

   `not_org_member`.
4. HCG Store deployed (PR #14 phase 3, Fly.io), with the permission mapping from §4 decided. Then Ship to Store uploads a
   real build as a **private draft**. Release approval stays manual in HCG Store, and Executable Maker never submits to
   TestFlight.
